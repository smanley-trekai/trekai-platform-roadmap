Topic 03

Current process

We already use GitHub Actions to preview some infrastructure changes.

Open a pull
request (PR)

Submit the code to
main or preston.

→
Run checks
and a plan

GitHub Actions shows
the proposed changes.

→
Review the PR

The team reviews
the code and plan.

→
Run apply
separately

The PR workflow
does not run apply.

Automatic plans currently cover changes in development folders.
We need to extend coverage to staging, production and affected shared code.

Plan shows what will change. Apply makes the change.

Proposed improvements

  • Show a plan for every infrastructure component affected by a change.
  • Use GitHub Actions to run the approved infrastructure changes.
  • Agree who reviews the code and who approves deployment
    to each environment.
  • Test the result before moving the change to the next environment.

We run a new plan after merge because the code or infrastructure

A successful apply means Terraform finished.
Testing confirms the change works as expected.

Who approves what

DecisionWhat the person approvesWho needs to be assigned
PR approvalThe code and the changes shown in the preview plans.The required code reviewers.
Apply approvalThe final plan for the selected environment.The people allowed to approve infrastructure changes.
Test acceptanceThe test results before the change moves to the next environment.The person responsible for the service or its testing.

Proposal: require final-plan approval for staging and production.
The team will decide whether development needs approval or can apply automatically.

Plan for production.
Approve, apply and test.

After tests pass, update the next environment to use the tested code
or shared module version. Generate a new plan for that environment.

Main holds the reviewed code. The Terraform folder, settings and state
determine which environment changes.

Every environment needs its own plan.
A development plan cannot be used for production.

How we test the change

Choose the tests based on what the change is supposed to do.

ExampleBefore applyAfter apply
DatabaseReview the database settings
and connection setup.		Confirm the settings and check

AccessReview who should have access

BackupsAgree the backup settings

CapacityAgree the expected workload

When something goes wrong

What happensWhat we do next
PR checks failThe developer fixes the code. Run the checks again
before approving the PR.
The final plan changes
or approval is denied		Stop the apply. Resolve the issue, create a new plan
if needed, and obtain approval again.
Apply failsDevOps checks what changed and plans the fix.
Review the fix before running it.
Tests failHold the change in the current environment.
Fix it and test again before moving forward.

Run only one apply at a time for the same Terraform state.

Decisions needed from the team

  1. Which development infrastructure should we use for the first rollout?
  2. Who reviews PRs, approves applies and accepts test results?
  3. Should development apply automatically after merge,
    or should someone approve it?
  4. Which tests must pass before we move to staging and production?

Next step: agree the development rollout, assign owners and begin the setup review.
