Proposed repository structure

A monorepo stores related projects in one Git repository.
Example name: devops. The team will agree the final name and layout.

FolderWhat goes here
terraform/Infrastructure code, separated by product and environment.
gitops/Application deployment configuration for each product.
automation/DevOps scripts and Ansible code that we agree to include.
.github/GitHub Actions workflows and code review rules.
docs/Setup instructions and operating procedures.

Scope and access

  • Start with the Terraform and GitOps repositories we agree to include.
  • Review scripts, Ansible and older infrastructure code before moving them.
  • Application source code belongs to the separate application
    monorepo proposals.
  • Keep code in a separate repository when it needs separate read access.
    Folder review rules do not restrict who can read the code.

Each environment keeps its own Terraform state, permissions and deployment rules.

How we know the move works

  • PRs run the correct checks and reach the required reviewers.
  • Application workflows write to the new location,
    and Argo CD reads the new configuration.
  • Terraform still uses the intended state and environment permissions.
  • Deployments and the recovery procedure work in the development test.
  • The team can find the code and follow the updated instructions.

Decisions needed from the team

  1. Do we want one repository, or separate repositories with shared workflows?
  2. Which code should move, and which code needs separate read access?
  3. What repository name, folder layout and code history approach will we use?
  4. Who owns each area, and which reviews and checks are required?
  5. Which development area moves first, who owns the move and recovery,
    and what must pass before we continue?

Next step: agree the approach and assign owners to review the proposed scope.
