The next addition is a repeatable, isolated environment
where QA can test a selected release.

QA: proposed setup

  • QA requests an environment from an approved template,
    choosing the product, release, size and expiry.
  • DevOps maintains the templates and limits.
    Start with DevOps approval of every final environment plan.
  • Automation runs Terraform with a scoped identity,
    then GitOps deploys the selected application versions.
  • QA receives the URL and status, then runs the tests.
    Approved expiry starts cleanup; failures go to DevOps.

Choosing what to test

A release manifest is a file that describes the test setup.

Release manifestWhat we record
Product and targetThe product, environment profile and instance name.
VersionsExact application images and infrastructure template version.
SetupSettings, dependencies, test data, accounts and secret references.
Test and lifecycleRequired tests, owner, capacity, budget and expiry or retention.

Use the same manifest to recreate the setup and identify the versions tested.

QA: who owns each part

RoleResponsibility
QARequest, test and report results. Choose approved options.
Request extensions or resets within the agreed policy.
DevOpsMaintain templates, workflows, permissions and limits.
Approve plans initially; resolve provisioning and cleanup failures.
AutomationRun Terraform under a scoped execution identity.
Deploy, check readiness, report status and perform approved cleanup.
Choose a Jira form or GitHub workflow that fits QA’s permissions.
Keep the request interface separate from infrastructure execution.

QA: how approvals evolve

Stage or requestProposed rule
Start with a pilotDevOps reviews every final target plan before automation applies it.
QA can request environments without DevOps building them manually.
Proven routine requestsAfter the team approves the policy, standard templates within
size, cost, data and expiry limits can proceed automatically.
Requests outside the limitsCustom configuration, larger capacity or sensitive data needs review.
DevOps routes approval to the responsible resource or data owner.
Prove isolation, limits, notifications and cleanup before expanding self-service.
Routine requests use approved policy; exceptions keep an approval gate.

Isolation and environment lifecycle

AreaProposed rule
Test isolationSeparate targets, data, identities and Terraform state.
Verify that shared services can tolerate the tests.
Reset and removalAutomate approved QA expiry cleanup and permitted resets.
Remove only owned resources; report failures to DevOps.
Demos and client pilotsUse separate profiles and schedules. Keep active pilot data.
Require owner approval before changes or retirement.
Before removal, stop GitOps from recreating the workloads.
Check for leftover resources and cost.

QA: decisions for the team

  1. Which product and test release should we start with?
  2. Which tests require dedicated infrastructure
    and which can safely share services?
  3. Who approves exceptions and owns failed setup or cleanup?
  4. Which data, size, cost and expiry limits allow routine requests
    to proceed under an approved policy?
