Stage 1 / How does an agent work?

How does an agent work?

01 What can an agent do?
Give it a goal and a test it can run. It can make a change, read the test result and try again. Tell it when to stop.
02 Where does its information come from?
A skill gives it a procedure. A plugin can bundle tools. MCP connects it to systems. Retrieval (RAG) finds documents, memory recalls past work, and logs and metrics show what the service is doing now.
03 Set the access boundary
For a staging investigation, give the agent read access to staging logs. Treat anything written in a log or ticket as evidence. Only the team can authorize more access.

Team practice · Give an agent a read-only CI question. Identify its tools, evidence and stopping condition.

Stage 1 / How does an agent work?

What changes when an agent can act?

An assistant can help draft a test. An agent with an authorized test runner can execute it, read the failure and revise the patch.

Engineer asks
“Make GET /catalog return the two IDs in this fixture. Work on this branch.”
Agent returns
A diff, the command it ran and the observed IDs. If the test fails, it traces the failure within the agreed scope.
Engineer decides
Inspect the diff and the failing-path test. Request a correction or send the change for review.

Where an agent gets its evidence

Retrieval (RAG)
Retrieve the part of the runbook that explains the catalog’s storage dependency. Give the agent the passage and its source.

A retained lesson suggests a prior bucket mismatch. Check the current revision and configuration before treating that lesson as fact.

What exactly is the task?

04 Pick one result you can check

Personal

Project

Stage 2 / What exactly is the task?

How much guidance gets loaded?

Team target
The roadmap suggests fewer than about 200 concise lines per AGENTS.md, often fewer at the root. This is a maintainability guideline.
Codex
Root-to-working-directory instructions share the default 32 KiB combined budget (project_doc_max_bytes). Within a directory, AGENTS.override.md takes precedence. Read guidance for sibling modules explicitly.
Claude Code
The documented recommendation is under 200 lines per CLAUDE.md. Ancestors load at startup and child guidance as the subtree is accessed. Path-scoped rules narrow applicability. Imports consume context.

Inspect the workspace with existing access

10 Check the actual permissions
If the task is read-only, check that the account and tools enforce it. Writing “read-only” in a prompt still leaves the account with its existing permissions.
11 Look before you edit
With tools you already have permission to use, find the handler, a similar change and the tests. Keep any new tool inactive while you review it.

People
Developers edit service branches. DevOps reviews environment plans. QA exercises test endpoints. Leads and managers review evidence within their assigned responsibilities.

Stage 4 / Is the tool safe, and does it help?

Is the tool safe, and does it help?

13 Is it safe to test?
Pin the version. Read its instructions, scripts and dependencies. Check what it can change and where it sends data. Use scans and a human review before running it in isolation.
14 Does it help on this task?
In a sandbox, try the same task with and without the tool. Compare correct answers, time, cost and unwanted actions. Include a case where the agent should leave the tool idle.
15 Write down the decision
Record who reviewed which version, the evidence and the allowed use. Enable it only if both checks pass. Check the record each time and review changes again.

Team practice · Before using a new CI capability, decide what would count as a safety pass and a usefulness pass.

Stage 4 / Is the tool safe, and does it help?

Inspect the inactive candidate

Skill
Freeze the version or hash. Read SKILL.md, references, scripts and dependencies as data. Combine manual review with appropriate static, dependency and secret scans.
MCP connection
Inspect the server or provider evidence, transport, authentication, exposed tools and destinations. In isolation, test allowed and denied actions, output handling, failures and credential revocation.
Plugin bundle
Inventory enabled skills, hooks, tools, dependencies and permissions. Examine secret access, unexpected execution, writes, network destinations and attempts to override the task.
Stage 4 / Is the tool safe, and does it help?

Compare the candidate with the current workflow

Set up a fair trial
After safety review, use dummy data in a sandbox without production credentials. Run equivalent prompts with and without the candidate. Hold inputs, model, settings and budget steady.
Measure the result
Use representative successes, failures and cases where the tool should stay idle. Score correctness, evidence, time, cost, unnecessary calls and unwanted actions. Repeat variable runs.
Decide and record
Both pass → use within the reviewed scope. A failure or unresolved evidence → hold or reject, then repair or choose an alternative and repeat the relevant checks.
Stage 4 / Is the tool safe, and does it help?

Can we use this tool again?

Record
Source, hash or version, dependencies, configuration, allowed task, data and resources. Attach coverage, findings, baseline results, decision, reviewer and date.
Before each task
Match the installed version, server behavior, permissions and intended purpose to the record. Hold use when the review is missing or the scope differs.
On change
Re-audit material changes to the version, dependency, server, permissions or configuration. After an authorized action, verify the outcome at the target.

Make the change and test it

16 Work through one change
Read the code, agree on a plan, make the change, test it and review the result. Use the tools and environment covered by the review.
17 Keep the patch small
If the ticket changes one handler, reuse its existing patterns. Leave unrelated upgrades for another ticket so the reviewer can see exactly what changed.
18 Check what actually happened
Compare the result with the ticket and the architecture. After deployment, call the endpoint in the intended environment. A green pipeline alone cannot tell you what the API returned.

Stage 5 / Make the change and test it

Follow one image across environments

Local → dev
Build in CI, record the digest, then compare the dev smoke-test response with the fixture.
Dev → staging
Promote the tested digest. Review staging configuration and its own Terraform plan when infrastructure changes. QA tests with staging identities and data.
Staging → production
Bring the evidence and recovery procedure to the release owner. After authorized rollout, verify the serving revision, errors, latency and a permitted functional check.

Review the evidence and hand it off

19 Get a second look
Give a fresh session or a separate review agent one question, such as “Which bucket can this identity read?” Ask for the exact line. The engineer checks the answer.
20 Leave the next person a handoff
Save what changed, why, what passed, what is still open and what to do next. Link the evidence from the ticket or task record.

Use the runbook to learn what should happen. Match a request to its logs, metrics and recent deployments to see what did happen. Label possible causes until you have evidence.

Stage 7 / What is worth repeating?

What is worth repeating?

22 Save a procedure that keeps working
If the same CI checks help on several tickets, write them as a skill. Record where to find it and review the new version before reuse.
23 Choose when the agent can act
Work together on an unfamiliar problem. Delegate a well-defined patch. For scheduled or event-triggered work, set a stopping point and decide who sees failures. Register hooks only where needed.
24 Check whether the team saved effort
Compare similar tickets. Count correct results, review time, rework and tool cost. Use that evidence to decide whether the agent should take on more or less work.

Team practice · Trial a proven procedure on comparable tasks. Use the measured results at step 24 to revisit the autonomy choice at step 23.

Stage 7 / What is worth repeating?

Package a procedure after it proves useful

Project skills
Codex uses .agents/skills/<name>/SKILL.md. Claude Code uses .claude/skills/<name>/SKILL.md. Keep scripts, assets and references beside the procedure.
Personal skills
Use ~/.agents/skills/ for Codex or ~/.claude/skills/ for Claude Code. Verify discovery in the client and re-audit the changed skill before reuse.
Plugins and state
Use supported installation and configuration mechanisms. Clients maintain plugin records, caches, history and generated memory. Maintain authoritative team rules in the repository.
Stage 7 / What is worth repeating?

Choose how the work starts and stops

Interactive or delegated
Work interactively while requirements are uncertain. Delegate a bounded patch once inputs, checks, permissions and stopping conditions are clear.
Scheduled or event-triggered
A scheduled job can propose a maintenance review. A failed CI run can trigger a read-only investigation. Bound attempts and time, deduplicate repeated events and route unresolved failures.
Registered hooks
Use a supported lifecycle event for an exact recurring check. Codex supports hooks.json registrations or inline TOML hooks. Claude Code registers hooks in settings. Explicitly register the script.
