Using AI agents for software development and cloud DevOps

Suppose your ticket says, “Build an API that reads a catalog from cloud storage.” What do you ask the agent to do first? Follow the example from a local test to a working service. Then see how the team investigates when the same API fails in staging.

The worked example uses a container, Terraform and Google Cloud. The paths, identities and environments below are illustrative. Use your project’s existing equivalents.

What would a successful ticket look like?

Break “deploy the catalog API” into three checks. Does the handler return the right IDs? Can the service read its bucket? Does a request work after deployment? Put the expected answers in the ticket so the agent knows how to test its work.

Prompt style for engineers

Write as you would to a teammate picking up a ticket. Lead with a verb that describes the assignment: plan, implement, review or diagnose. Name the repository or environment, point to the evidence, and describe a result someone else can check. A few precise sentences are enough.

A pattern you can copy

[Action] [one outcome] in [repo, branch or environment]. Start with [contract, diff, plan or run link]. You may [allowed actions]. Verify by [observable check]. Return [artifact or finding] with [evidence]. If [material uncertainty or scope boundary], stop there and report [what you need].

Use the agent to sharpen a rough request

My draft is “fix the staging deploy.” Rewrite it as a read-only investigation prompt. Preserve the facts I supplied. Leave placeholders for the service, failed run and expected behavior. Ask me only for missing details that would change the investigation. Return the prompt for me to review before work starts.

What to expect. The assistant returns an editable draft and the missing facts. Supply the run link, check the environment and permissions, then use the revised prompt to start the investigation.

Read the rewrite once for intent. For example, if the smoke test failed after deployment completed, say exactly that. It tells the engineer or agent to begin with the failing request and serving revision. When new evidence comes in, a short follow-up works well: “The digest matches the last healthy run. Compare the staging bucket reference and runtime identity across those two revisions. Cite the difference you find.”

New project · get one API request working

1. Agree on behavior with QA

You ask
“Use this contract and synthetic catalog fixture to draft acceptance cases for a successful request and unavailable storage. Show the expected status and body for each.”
Agent returns
A small test matrix tied to the fixture, plus any response behavior the contract leaves open.
You decide
QA and the developer confirm the two expected IDs, the 503 response and which storage details must stay private. Resolve ambiguities before asking for code.

2. Implement and test on a branch

You ask
“Implement GET /catalog on this branch using the existing storage abstraction. Run the agreed cases with the fixture. Return the diff, test command and results.”
Agent returns
A reviewable application patch and test output for both paths.
You decide
Read the failure test. If it bypasses the handler, ask the agent to exercise the handler through its normal entry point. Once checks pass, verify the CI build and give DevOps the image digest.

3. Prepare the dev infrastructure change

You ask
“Use this digest and the existing Terraform modules to draft the Cloud Run change. Show the dev project, state target, ingress, runtime identity, bucket permissions and resource changes. Stop at the plan.”
Agent returns
An infrastructure diff and the approved pipeline’s plan reference, with any replacement, access expansion or cost-relevant setting called out.
You decide
Inspect the plan itself. Confirm the runtime identity can read the intended dev bucket and the deployment identity is separate. If the target or permission is wrong, request a revised plan before apply. Keep sensitive plan output in its approved store.

4. Verify the deployed service with QA

You ask
“The approved pipeline has deployed to dev. Use the authorized test identity and fixture to run the smoke test, or read the QA run I supplied. Match the request to the serving revision.”
Agent returns
The expected and observed IDs, status, request reference and serving image digest, with the source of each observation.
You decide
Compare the IDs with the fixture and the digest with the CI build. Attach the evidence if both match. If they differ, use the request reference to investigate before promoting.

Ongoing project · why is staging returning 503?

The dev checks passed. In staging, the deployment completed and the smoke test for GET /catalog returned 503. Start a read-only investigation. The findings below illustrate one possible cause.

1. Identify the request and revision

You ask
“Here are the failing staging smoke test and last healthy run. Which request failed, when, and which revision handled it? Compare its digest with the intended CI artifact.”
Agent returns
A request ID or timestamp and links to the test, deployment and serving revision. Missing evidence is marked.
You decide
If the digest differs, investigate traffic assignment or the pipeline input. If it matches, use the request reference to trace the application failure.

2. Test the first explanation

You ask
“Show the earliest failed operation for this request. Which log entry supports it, and what is still uncertain?”
Agent returns
For example, a denied read from storage, with the relevant log reference. Possible causes include the bucket selection and the runtime identity.
You decide
Check the log entry. Ask for a configuration comparison before deciding whether any IAM change is warranted. If logs are unavailable, request a sanitized excerpt from the operator.

3. Locate the configuration difference

You ask
“Compare the bucket reference and runtime identity on the failing and last healthy staging revisions. Point to the version-controlled change that explains the difference.”
Agent returns
In this example, the staging reference changed to the dev bucket. The agent links the manifest diff to the deployed configuration.
You decide
Confirm the intended staging bucket in the environment definition. Choose a staging configuration fix that preserves the existing environment boundary.

4. Delegate the fix on a branch

You ask
“Correct the staging bucket reference on a branch. Add a configuration check for the intended target. Return the diff, check result and staging plan or deployment diff. Stop before deployment.”
Agent returns
A scoped patch with a reproducible check and evidence of the resources or settings affected.
You decide
Inspect the target, permissions and diff. Route the reviewed change through the existing staging pipeline.

5. Verify and close

You ask
“Using the original staging test identity and fixture, compare a fresh run with the failed request. Report the status, fixture IDs and revision.”
Agent returns
Evidence that the corrected revision served the expected response, or the exact check that still fails.
You decide
Close the ticket when QA confirms the original symptom is resolved. If the symptom persists, keep the ticket open and use the new request reference for the next investigation.

Which tools and permissions does this job need?

Ask what is missing. If the test runner can already test your code, use it. If you need instructions for reviewing a Terraform plan, look for a skill. If you need a current CI log, a reviewed MCP connection may give you access. A plugin can package either one. DevOps HQ catalog

Try a plan-review skill on two examples. First inspect its version, scripts, dependencies, permissions and data destinations. Once it is safe to test, give it two sanitized plans: one grants too much access, and one is routine. Does it find the exact resource? Does it raise a false alarm? Compare its answers with your normal review. Record the result and allowed scope. Check that record before reuse and review material changes again. Audit record template

Map team responsibilities to access. Developers need service code and branch checks. DevOps engineers need environment definitions and relevant pipeline evidence. QA needs the test endpoint, fixtures and results. Leads, managers and directors use the release evidence to make decisions within their assigned responsibility. Where Entra ID supplies workforce identity, map the appropriate groups to target IAM roles for each environment. Use PAM for approved temporary elevation. Independently scope the CI plan identity, deployment identity and application runtime identity. Enforce these limits in the connected systems.

Hand off a release someone else can verify

Could another engineer trace this ticket to the code change, the deployed image and a successful request? Give a fresh agent session those links. Ask it to flag any missing evidence before the release owner decides.

Change               Ticket, app PR, infrastructure PR, commit and image digest
Target               Environment, cloud project, service, IaC state and revision
Before rollout       Test results, target plan or deployment diff, outstanding risks
After rollout        Smoke-test run, expected and actual response, telemetry window
Recovery             Last healthy image and config, rollback trigger, recovery check
Handoff              Current delivery state, next action and responsible team

For an application regression, the runbook might restore traffic to the previous healthy revision. For a configuration or IAM change, review the corrective infrastructure plan as well. Switching the image alone can leave the failing configuration in place. Verify recovery with the original failing request.

You ask
“Use the PRs, build, deployment and smoke-test links to fill in the handoff above. Mark missing evidence and identify the recovery check for this change.”
Agent returns
A release record linking commit, image, revision and outcome, plus any gaps.
You decide
Open the links and verify they refer to the same target. If a run is missing, request it or record the handoff as pending verification.

Save task context where the next engineer can find it

Imagine a teammate asks, “Why does staging have its own catalog bucket?” They should be able to open the repo, find the ticket and see the decision. Put a link in the root instructions to a task index. For each important change, save a short dated record and link the evidence.

3. Test the handoff in a fresh session

You ask
“Starting from the repo instructions, find prior work on a staging catalog 503. Explain the confirmed cause at the time, cite the fix and its test, and identify what you would check on the current revision before proposing another change. Work read-only.”
Agent returns
The matching task record, PR or commit, historical verification, and a current check such as comparing the serving revision’s bucket reference with today’s staging definition. It flags any inaccessible evidence.
You decide
If the agent finds the record without being given its filename and can distinguish the historical fix from current behavior, the handoff works. If it misses the record, add the missing search term or repair the entry-point link and try again.

When should we automate this?

Work alongside the agent the first time you investigate a service. Once you know the checks, delegate a small patch. If CI failures repeat, try a read-only summary that links the failed step and logs. Limit retries, group duplicate events and send unresolved failures to a person. Compare time to the right diagnosis, review effort, false leads and cost before automating more.

Keep verified conventions in project instructions, current evidence in the ticket, and a repeatable procedure in a reviewed skill. For the full learning sequence and supporting concepts, see the learning roadmap and the AI workflow guide.
