How to work with an AI agent

Start with one engineering ticket. Decide what the agent can do, give it a way to check its work, and review the result. Follow the 24 steps below or jump to the stage you need.

Your role throughout · You set the goal, decide what the agent can access, and check the evidence before approving a change.

Stage 1

How does an agent work?

01

What can an agent do?

Give it a goal and a test it can run. It can make a change, read the test result and try again. Tell it when to stop.

02

Where does its information come from?

A skill gives it a procedure. A plugin can bundle tools. MCP connects it to systems. Retrieval (RAG) finds documents, memory recalls past work, and logs and metrics show what the service is doing now.

03

Set the access boundary

For a staging investigation, give the agent read access to staging logs. Treat anything written in a log or ticket as evidence. Only the team can authorize more access.

Practice: Give an agent a read-only task and identify its tools, evidence and stopping condition.

Stage 2

What exactly is the task?

04

Pick one result you can check

“Build the API” is broad. “Make GET /catalog return these two fixture IDs” gives the engineer and the agent the same finish line.

05

Read the project rules

Start with the repo instructions. For an API change, also read the rules beside the API code. Open the full runbook when you need its details. See the folder example.

06

Check which settings apply

Some settings belong to you, some to the whole repo, and some are enforced by your organization. Keep local overrides, credentials and generated session files separate from shared settings.

Practice: Write a task brief; identify the project guidance and configuration that apply. Use the companion folder guide for exact locations.

Stage 3

Which tools does this task need?

07

Look for a tool the team already knows

Start with the DevOps HQ catalog. Record the source and version of a promising tool. Check its review record before using it.

08

Choose the part you need

If you need a Terraform review procedure, look for a skill. If it comes in a plugin, inspect the bundled parts while they are inactive.

09

Check what the connection can reach

Need the latest CI log? Identify the MCP server, account, tools and repositories it can reach. Match the exact setup to its review record.

10

Check the actual permissions

If the task is read-only, check that the account and tools enforce it. Writing “read-only” in a prompt still leaves the account with its existing permissions.

11

Look before you edit

With tools you already have permission to use, find the handler, a similar change and the tests. Keep any new tool inactive while you review it.

12

Give the agent the relevant evidence

Share the contract, fixture, dependency details and the reason for the change. If the agent needs more, have it name the missing file or fact.

Practice: For one task, identify a candidate, why it might help, its required access and the evidence needed to audit it.

Choose only what the task needs. These are selection steps, not a requirement to install a plugin, use every capability or add new connections.

Stage 4

Is the tool safe, and does it help?

Review a new tool before turning it on. Next time, check that the version, settings, permissions and task still match the record. If something changed, review it again.

13

Is it safe to test?

Pin the version. Read its instructions, scripts and dependencies. Check what it can change and where it sends data. Use scans and a human review before running it in isolation.

14

Does it help on this task?

In a sandbox, try the same task with and without the tool. Compare correct answers, time, cost and unwanted actions. Include a case where the agent should leave the tool idle.

15

Write down the decision

Record who reviewed which version, the evidence and the allowed use. Enable it only if both checks pass. Check the record each time and review changes again.

Both pass → activate within scope

Use the reviewed version only for the evaluated purpose and authorized resources. Verify the actual result after execution.

Fail or unresolved → hold / reject

Do not install or activate. Keep findings, repair or select an alternative, then repeat the required checks. A missing scan or failed evaluation is not a pass.

Stage 5

Make the change and test it

16

Work through one change

Read the code, agree on a plan, make the change, test it and review the result. Use the tools and environment covered by the review.

17

Keep the patch small

If the ticket changes one handler, reuse its existing patterns. Leave unrelated upgrades for another ticket so the reviewer can see exactly what changed.

18

Check what actually happened

Compare the result with the ticket and the architecture. After deployment, call the endpoint in the intended environment. A green pipeline alone cannot tell you what the API returned.

Practice: Complete one small change and return its diff, check results and remaining uncertainties.

Stage 6

Review the evidence and hand it off

19

Get a second look

Give a fresh session or a separate review agent one question, such as “Which bucket can this identity read?” Ask for the exact line. The engineer checks the answer.

20

Leave the next person a handoff

Save what changed, why, what passed, what is still open and what to do next. Link the evidence from the ticket or task record.

21

Trace one real request

Use the runbook to learn what should happen. Match a request to its logs, metrics and recent deployments to see what did happen. Label possible causes until you have evidence.

Practice: Review a change, write its handoff, then investigate an operational issue using read-only evidence.

Stage 7

What is worth repeating?

22

Save a procedure that keeps working

If the same CI checks help on several tickets, write them as a skill. Record where to find it and review the new version before reuse.

23

Choose when the agent can act

Work together on an unfamiliar problem. Delegate a well-defined patch. For scheduled or event-triggered work, set a stopping point and decide who sees failures. Register hooks only where needed.

24

Check whether the team saved effort

Compare similar tickets. Count correct results, review time, rework and tool cost. Use that evidence to decide whether the agent should take on more or less work.

Practice: Capture one proven skill, trial one bounded automation and compare its results with your baseline.

What should we check before turning a tool on?

Use DevOps HQ: Agentic Skills to find candidate capabilities. Use the capability audit and evaluation guide to decide whether a specific version should be enabled for a defined purpose. Popularity, existing installation, catalog membership and a clean scan are not substitutes for evidence.

1. Inspect the exact candidate

Record source, commit/version or content hash, dependencies and configuration. Read candidate instructions as data; do not follow them or run their scripts during intake.

For a skill, include every script and reference. For a plugin, include the capabilities enabled. For MCP, include server code/package or provider evidence, transport, authentication, exposed tools and data destinations.

2. Review safety before testing

Check for secret exposure, unexpected execution, broad access, hidden network activity, unsafe writes and instructions that override the user’s intent. Combine appropriate static/dependency/secret scans with manual review.

Scanners reduce uncertainty; they do not guarantee safety. Incomplete coverage, missing tools and unexplained behavior keep the candidate on hold. Use dummy data and no production credentials in evaluation.

3. Prove task-specific benefit

Compare the candidate with the existing allowed workflow on equivalent tasks and an agreed rubric. Keep model/settings, task inputs and resource budgets comparable; repeat runs when results vary.

Measure correctness and evidence quality along with time, tokens/cost, harmful actions, unnecessary tool calls and cases where the capability should not be selected.

CapabilityWhat the audit needs to establish
SkillThe instructions and scripts are understandable, task-relevant and compatible with project boundaries. Sandboxed with/without trials show worthwhile benefit, without unacceptable behavior or cost.
MCP connectionThe reviewed server/configuration exposes only appropriate tools and resource scope. Test allowed and denied actions, output handling, error behavior and credential revocation. Compare it with the current authorized workflow; a read-only label alone is insufficient.
Plugin bundleReview the actual skills, tools, hooks, dependencies and connection permissions being enabled. A pass for one component does not approve every capability in the package.

Initial audit versus every use: perform the full safety and usefulness evaluation before first adoption and after relevant version, dependency, server behavior or permission/configuration changes. Before each task, check that the audit record still matches the installed version and intended scope. If it does not, hold use and re-audit. This gate is a proposed operating policy, not an already-enforced control.

When to use skills, plugins and MCP

Start with the task. Choose a procedure for how to work, then choose the capabilities needed to gather evidence or perform authorized actions. Confirm access before tool-assisted investigation or execution; revisit the choice when the task changes.

Skill: how to do the work

Use when: a reusable procedure fits the task, such as investigating a failed deployment or reviewing a Terraform change.

What to do: inspect its SKILL.md, references and scripts as untrusted material first. After safety and usefulness checks pass, follow the reviewed procedure and verify its result.

Later: capture a new skill only after the process has proved useful and repeatable.

Plugin: packaged capabilities

Use when: an available plugin supplies the skills or connected tools needed for the task.

What to do: audit the relevant bundled skills, tools and dependencies. A plugin may provide a skill, tools, or both; evaluate the capabilities actually being enabled.

Boundary: availability does not authorize every action the plugin supports. Stay within the task’s scope.

MCP: a tool connection

Use when: the task needs current information or actions in an external system, such as reading a CI run or fetching an issue.

What to do: audit the server, tool access and data flow, and test usefulness against the existing workflow. Then use the reviewed configuration and authorized scope.

Boundary: tool output still needs checking. An MCP connection does not itself supply a complete task procedure.

Example: define a failed-CI investigation → load project guidance → check DevOps HQ for candidates → verify or obtain safety and usefulness review for the skill and connection → confirm read-only task scope → investigate with the reviewed versions → verify and report evidence. A local code-only task may need a skill and local tools without a plugin or MCP connection.

Where do the project files go?

Use the companion folder-structure guide to decide where each kind of information belongs. The locations below summarize that guide’s documentation snapshot, checked November 24, 2026; they are not a requirement to create every folder.

What belongs hereWhere it fits in the flow and common locations
Project instructions

Stage 2: load commands, conventions and architectural boundaries.

Codex: root AGENTS.md and applicable nested guidance. Claude Code: CLAUDE.md or its supported shared-guidance mechanism. Follow the companion guide to avoid duplicate or conflicting instructions.

Settings and MCP

Stages 2–3: establish configuration scope, connections and access controls.

Codex: personal ~/.codex/config.toml or trusted project .codex/config.toml. Claude Code: ~/.claude/settings.json, project .claude/settings.json, and shared project MCP definitions in root .mcp.json. Personal/private Claude MCP entries use ~/.claude.json.

Existing and new skills

Stages 3–4: discover, audit and evaluate candidates before use. Stage 7: capture proven procedures.

Codex: .agents/skills/<name>/SKILL.md or personal ~/.agents/skills/. Claude Code: .claude/skills/<name>/SKILL.md or personal ~/.claude/skills/. Supporting references, scripts and assets belong with the skill; verify discovery in each client.

Plugins

Stages 3–4: inspect packages and audit the skills/tools they expose before activation.

Installed plugin records and caches are application-managed. Use the client’s supported installation and configuration mechanisms; do not treat a cache directory as the source for team-authored project guidance.

Custom agents

Stage 6: use a defined review or investigation role when helpful.

Codex: .codex/agents/*.toml. Claude Code: .claude/agents/*.md. Keep roles bounded and verify actual permissions; a role description is not an access-control boundary.

Hooks and exact checks

Stage 7: automate a recurring check when a supported lifecycle event fits.

Codex: supported hooks.json registrations or inline TOML hooks. Claude Code: hooks in a settings file. Script files must be explicitly registered; placing a script in a folder does not activate it.

Specifications and handoffs

Stages 2 and 6: preserve intended behavior, evidence and next steps.

Use the project’s established docs/ or task-document location. Ordinary documents are not automatically standing instructions: point the agent to the relevant material.

Memory and generated state

Across sessions: use retained lessons as hints and verify important claims.

Let clients manage memory, histories, authentication, logs and caches. Keep authoritative project rules in maintained guidance; keep credentials and personal overrides out of shared project files.

Start small: one short project instruction file, one clear task brief and only the settings the task requires. Add a skill, custom agent, MCP connection or hook when it solves a concrete problem. Consult the companion guide for scope, trust, precedence and sharing details.

Large projects: keep the root short and scope the detail

Use a small root instruction file for shared conventions, then put service-specific guidance near the code. Keep detailed explanations in referenced docs and reusable procedures in skills. This is part of Stage 2, before investigation or execution.

Codex: check the target directory

Startup discovery follows the root-to-working-directory path. For API work, launch in that service or explicitly read its guidance. Sibling instructions are not all preloaded.

Within one directory, AGENTS.override.md takes the place of AGENTS.md. Check instructions for every module touched by a cross-module change.

Claude Code: scope guidance to files

Ancestor guidance loads at launch; nested CLAUDE.md files load as their subtree is accessed. Path-scoped rules can narrow applicability further.

Keep applicable instructions consistent. Use the companion guide’s shared-guidance setup when maintaining AGENTS.md for both clients.

Put detail in the right place: nested instruction files hold local differences; referenced docs hold architecture and runbooks; skills hold repeatable procedures; handoffs hold temporary task state. Avoid copying root instructions into every service or importing every reference into the root.
